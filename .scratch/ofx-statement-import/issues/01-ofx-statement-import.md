# 01 — OFX statement import (Importar Extrato)

**What to build:** An "Importar extrato" action on the Transações page: upload an OFX file, pick the `Conta` and `Responsável` the file belongs to, review a staging list of parsed transactions (category per row, duplicates flagged, transfers excluded), then confirm to insert the checked rows into the register.

**Blocked by:** None — can start immediately

**Status:** done

- [x] Migration adds `external_id text` (nullable) to `transactions`, plus a partial unique index on `(account_id, external_id) where external_id is not null`
- [x] `parseOfxStatement(ofxText)` — pure function, no I/O — parses `STMTTRN` blocks (OFX 1.x SGML dialect) into `{ date, amount, type, description, fitid }` rows; derives `type` from `TRNTYPE` (fallback: `TRNAMT` sign); drops `TRNTYPE = XFER` rows entirely
- [x] `importTransactions(supabase, { householdId, accountId, ownerHouseholdMemberId, rows })` — for each included row, checks `fitid` against existing `external_id` for that `accountId`; inserts non-duplicate rows; returns inserted vs. skipped
- [x] Upload UI: file input + `Conta` picker + `Responsável` picker, all required
- [x] Staging list (server-rendered, no client-side state): one row per parsed transaction — date/amount/type read-only, category `<select>` (same options as the manual transaction form), include checkbox defaulted checked, defaulted unchecked + "já importado" label for a detected duplicate
- [x] Confirm submits the staging form to a second server action, calls `importTransactions`, redirects to the Transações list showing the newly-inserted rows
- [x] Expense rows with no category are rejected on confirm, same as manual entry (check constraint + server-action validation)
- [x] An unparseable/invalid OFX file shows an error instead of silently importing bad data
- [x] Import is scoped to the signed-in household (account/owner from another household rejected)
- [x] Existing manual single-transaction entry form is untouched and still works
- [x] `parseOfxStatement` unit tests: normal debit/credit row, `XFER` exclusion, multiple `STMTTRN` blocks, malformed/missing `FITID`, negative-vs-positive `TRNAMT` sign
- [x] `importTransactions` integration tests (real Supabase, pattern from `create-transaction.test.ts`/`post-due-recurring-transactions.test.ts`): normal batch insert, same `fitid` + same account skipped on re-import, same `fitid` + different account not treated as duplicate, expense with no category rejected, cross-household account/owner rejected

## Comments

Implemented in commit `73c4d5c`.

- New migration `supabase/migrations/20260727000000_transactions_external_id.sql` — `transactions.external_id text` nullable + `transactions_account_id_external_id_idx` partial unique index on `(account_id, external_id) where external_id is not null`. Applied directly to the hosted project (`xzmmsjpqalrwonqbuzul`) via `apply_migration` before commit.
- `src/domain/ofx/parse-ofx-statement.ts`: regex-based SGML tag extraction (`<STMTTRN>…</STMTTRN>` block split, then `<TAG>value` up to the next `<`/newline per child tag, since OFX 1.x child tags have no closing tag). `TRNTYPE` mapped to expense/income via two known-value sets, falling back to `TRNAMT` sign for absent/unrecognized types. Rows missing a parseable date or amount are skipped rather than fabricated; a missing/malformed `FITID` comes back `null` rather than failing the row. Throws only when the input has no `<OFX` tag at all (not a "this file has zero transactions" case). 8 unit tests, all passing.
- `src/domain/ofx/import-transactions.ts`: single bulk insert (not one-by-one) so a bad row (e.g. expense with no category) fails the whole batch atomically via the table's check constraint, matching manual entry's behavior. Cross-household account/owner rejection reuses the existing `transactions_check_household_consistency` trigger — no new isolation logic needed. `findExistingExternalIds` is exported and shared between the upload action's display-only duplicate flagging and this function's actual insert-time guard, so the two can't drift apart. 6 integration tests written (pattern from `create-transaction.test.ts`) — **could not be run**: local Supabase/Docker is unavailable in this environment (pre-existing limitation, not introduced by this change), so these are inspected/reasoned through rather than green-checked locally.
- UI at `src/app/dashboard/transactions/import/` (`page.tsx`/`actions.ts`/`ofx-upload-form.tsx`/`ofx-staging-form.tsx`/`batch-codec.ts`), linked from a new "Importar extrato" button on the Transações page. Two-step flow on one route: upload posts to `uploadOfxAction`, which parses + flags duplicates + redirects (POST-redirect-GET) to the same page with the rows base64url-encoded in a `batch` query param — no staging DB table, no client-side JS state, matching the ticket's "server-rendered, no client-side state" requirement. The review form round-trips every row field (date/amount/type/description/fitid) as hidden inputs; only `categoryId` and `include` are live user input. `Responsável` has no blank/"Compartilhado" option here (unlike the manual form) since the ticket requires it for the whole batch.
