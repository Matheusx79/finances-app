# 08 — Recurring transaction templates + auto-post

**What to build:** Let household members set up a recurring transaction template (amount, category, account, owner, monthly frequency keyed off a day-of-month), and have a scheduled job auto-post a real, editable transaction from each active template when its due date arrives.

**Blocked by:** 04.

**Status:** done

- [x] Domain-layer functions: `createRecurringTemplate`, `updateRecurringTemplate`, `pauseRecurringTemplate`, `deleteRecurringTemplate`, `postDueRecurringTransactions`, tested against the local Supabase stack
- [x] A template records: amount, category, account, owner (member or shared), day-of-month frequency, active/paused flag
- [x] UI (in pt-BR) to create, edit, pause, and delete recurring templates
- [x] A scheduled job (e.g. Vercel Cron or Supabase scheduled function) runs at least daily and auto-posts a normal transaction for any active template whose due date has arrived
- [x] The auto-posted transaction references its originating template, and is otherwise a normal transaction — editable and deletable like any manually entered one
- [x] A paused template does not auto-post
- [x] Test coverage includes the due-date posting logic itself (e.g. a template due today posts, one due next month does not)

## Comments

Implemented in commit `4e911ec`.

- New migration `supabase/migrations/20260726200000_recurring_templates.sql` adds `recurring_templates` (`household_id`, `type`, `amount`, `category_id`, `account_id`, `owner_household_member_id`, `day_of_month` 1-31, `active` default true, `created_at`), same RLS/household-consistency-trigger shape as `transactions`/`category_budgets`, plus a nullable `transactions.recurring_template_id` (`on delete set null` — deleting a template later must not retroactively touch transactions it already produced, per "editable/deletable like any other"). Deliberately no `last_posted_year`/`month` bookkeeping column on the template — idempotency is derived from `transactions.recurring_template_id` instead, avoiding a second source of truth that could drift from the transactions table itself.
- Domain layer `src/domain/recurring/{types,create-recurring-template,update-recurring-template,pause-recurring-template,resume-recurring-template,delete-recurring-template,list-recurring-templates,post-due-recurring-transactions}.ts`, matching the `create-transaction`/`set-category-budget` plain-function convention. `resumeRecurringTemplate` was added beyond the ticket's literal function list (pause with no reverse action is a dead end for the UI) — flagged as a deliberate, reasonable scope addition by both the implementing agent and the Spec-axis review, not hidden.
- `postDueRecurringTransactions` due-date rule: due once `today`'s day-of-month reaches `min(template.day_of_month, daysInThatMonth)` — short months clamp to the last day (day 31 posts on day 30 in April) rather than skipping the month. Idempotency: checks for an existing transaction referencing the template within the current calendar month before inserting, so repeated daily cron runs on/after the due date don't double-post. The posted transaction is dated to the (possibly clamped) nominal due date, not whatever day the job actually ran, so a delayed catch-up run still lands correctly. 13 tests: due-today posts, not-yet-due doesn't, idempotent same-month re-run, posts again in a later month, short-month clamping, paused doesn't post, household-scoped isolation, and the no-`householdId`-scans-every-household cron path.
- UI at `src/app/dashboard/recurring/` (`page.tsx`/`actions.ts`/`recurring-template-form.tsx`), linked from the dashboard nav alongside "Orçamentos". List shows each template with pause/reativar and delete, plus inline `<details>`/`<summary>` edit — same pattern as the transactions page.
- Cron: `src/app/api/cron/post-recurring/route.ts` (`GET`, `Authorization: Bearer <CRON_SECRET>` check, service-role admin client since a scheduled job has no user session), looped per-household so one household's failure doesn't block the rest. `vercel.json` declares a daily 06:00 schedule. `CRON_SECRET` appended to `.env.local`; the same value still needs to be added to the Vercel project's environment variables by hand (can't be set remotely from here).

This meant the cron route's own auth check never even ran; every request to it, correctly authorized or not, got a 307 to `/login`. Only caught by actually curling the endpoint (`tsc`/`eslint`/unit tests can't see middleware routing). Fixed with a one-line matcher change excluding `api/` from the session middleware, mirroring the existing `manifest.webmanifest`/`sw.js` exclusion from ticket 09 (`f27c2fe`) — same class of bug, same fix shape. Confirmed after the fix: no `Authorization` header → 401 from the route's own check; correct header → posts; posting twice in a row → second call posts 0 (idempotent).
