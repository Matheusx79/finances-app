# 04 — Transaction entry (manual, expense & income) + recent feed

**What to build:** A form to manually log a transaction — amount, date, type (expense/income), category, account, owner (one household member or "shared"), and an optional note — plus editing and deleting existing transactions, and a recent-transactions feed on the dashboard.

**Blocked by:** 02, 03 (needs real accounts and categories to assign transactions to).

**Status:** done

- [x] Domain-layer functions: `createTransaction`, `updateTransaction`, `deleteTransaction`, `listTransactionsForMonth`, tested against the local Supabase stack
- [x] A transaction records: amount (BRL), date, type (expense or income), category (required for expenses), account, owner (household member A, B, or shared), optional note
- [x] UI (in pt-BR) to add a transaction, with category/account pickers populated from tickets 02/03
- [x] Either household member can edit or delete any transaction, regardless of who logged it
- [x] Dashboard shows a feed of recent transactions for the current month, newest first
- [x] Transactions are scoped to the household

## Comments

Implemented in commit `35039b2`.

- New migration `supabase/migrations/20260726180000_transactions.sql` adds a `transactions` table (`household_id`, `type`, `amount`, `date`, `category_id`, `account_id`, `owner_household_member_id`, `note`, `created_at`), scoped by RLS to `internal.household_id_for_user((select auth.uid()))` with explicit select/insert/update/delete policies and explicit grants to `authenticated`/`service_role` — same shape as the accounts/categories migrations. Per tickets 02/03's pre-documented decision, `account_id`/`category_id` FKs use `on delete restrict` (deleting a referenced account/category is blocked, not cascaded/nulled).
- **Amount storage decision:** `numeric(12, 2)` reais (e.g. `12.50`), not integer cents. The UI collects/displays a decimal BRL amount directly, so this avoids a cents↔reais conversion layer while still avoiding the float-rounding issues a `real`/`double precision` column would introduce.
- **Owner/shared modeling decision:** a nullable FK, `owner_household_member_id → household_members(id)`, rather than a text/enum column. A specific `household_members.id` means "this member owns/logged this transaction"; `null` means "shared." This ties the owner to the real member row (and its `display_name`) instead of introducing a second, parallel source of truth for member identity. `on delete restrict` since a member row disappearing out from under existing transactions should never happen silently.
- **Category-required-for-expense decision:** enforced with a table check constraint (`(type = 'expense' and category_id is not null) or (type = 'income')`) rather than splitting into two tables. On the UI side, the category `<select>` is always shown (there's no client-side JS in this form to conditionally hide/require it based on the type field) with a label hint ("obrigatória para despesas"); the actual requirement is enforced server-side in the form action (redirects back with a pt-BR error message, same `?erro=` pattern as the login form) and, as a backstop, by the DB check constraint.
- **Household-consistency trigger (added after code review, see below):** `internal.check_transaction_household_consistency()`, fired `before insert or update on transactions`, verifies `account_id`/`category_id`/`owner_household_member_id` each belong to the *same* household as the transaction. The plain FKs alone only guarantee the referenced row exists somewhere, not that it's in the right household — RLS on `transactions` only checks the transaction row's own `household_id`. Implemented as a trigger (mirroring the `seed_default_categories`/`household_member_cap` trigger style already established in this schema) since a cross-table check isn't expressible as a plain column check.
- Domain layer: `src/domain/transactions/{create-transaction,update-transaction,delete-transaction,list-transactions-for-month}.ts`, each with a colocated `*.test.ts` run against the real local Supabase stack, following the `src/domain/accounts`/`src/domain/categories` plain-function convention (a `types.ts` with a `toTransaction` row-mapper and a shared `TRANSACTION_COLUMNS` select-string constant, reused by create/update/list). Coverage includes: household-scoped isolation for every function, either-member-can-edit/delete-regardless-of-creator tests, cross-member read-visibility tests (a transaction created by one member is listed by the other), month-boundary tests (last day of a month vs. first day of the next, plus a December→January year-boundary case), and — added after code review — tests asserting an account/category/owner belonging to a different household is rejected.
- Extended `src/domain/household/types.ts`/`get-household-for-user.ts` to include each member's `household_members.id` (not just `userId`/`displayName`) — needed as the owner-picker's value/FK target. Updated `get-household-for-user.test.ts` accordingly. Extended `src/lib/current-household.ts`'s `requireHousehold()` to also return the full `household` object (additive; existing callers in `accounts`/`categories` are unaffected).
- UI at `src/app/dashboard/transactions/` (`page.tsx` + `transaction-form.tsx` shared between add/edit + `actions.ts`), linked from the dashboard alongside "Contas"/"Categorias". A shared `src/components/transaction-summary.tsx` renders the date/type-colored-amount/category-account-owner/note line for both the transactions list and the dashboard's recent-feed card, so the two views can't drift. `src/lib/currency.ts` adds `formatBRL` (`Intl.NumberFormat("pt-BR", { style: "currency", currency: "BRL" })`) and a manual-string `formatDateBR` (deliberately not `new Date(...).toLocaleDateString()`, to avoid a timezone-driven day shift on a plain `date` column value). Edit is a per-row `<details>`/`<summary>` disclosure (zero client JS) holding the same form pre-filled; delete is a plain form button — same pattern as accounts/categories' inline rename/delete.
- Dashboard (`src/app/dashboard/page.tsx`) now fetches accounts/categories/`listTransactionsForMonth` for the current month (only when the user has a household — it can't use the shared `requireHousehold()` helper itself, since that redirects to `/dashboard` on no-household, which would loop on this exact page) and renders the recent-transactions feed via `TransactionSummary`.
- Code-reviewed (Standards + Spec axes, parallel sub-agents) before commit.
  - **Standards axis:** no hard violations — domain layer matches the accounts/categories template exactly (no dead `.single()` branches, a `to<Thing>` mapper, colocated tests). Flagged two judgement-call smells at Rule-of-Three scale (dashboard vs. transactions page both computing the current month / fetching the same three lists; `{accounts, categories, members}` traveling together as a prop clump) — left as-is, same call ticket 03 made on similar duplication at two instances.
  - **Spec axis:** found two real gaps, both fixed before commit: (1) `listTransactionsForMonth` had no cross-member visibility test (transaction created by A, read by B) — added. (2) transactions could reference another household's account/category/owner id since the FKs don't check household membership by themselves — fixed with the `check_transaction_household_consistency` trigger described above, plus three new rejection tests (account/category/owner each belonging to a different household). A third, minor finding (missing-amount/date/account silently no-ops in the server action rather than showing an error) was left as-is — it matches the existing silent-no-op-on-invalid-required-field precedent already used in `accounts/actions.ts`/`categories/actions.ts`, and browser-level `required`/`type=number`/`type=date` validation makes it unreachable through the normal form UI; only the domain-specific category-required-for-expense rule (which the HTML form can't self-enforce) gets the explicit pt-BR error message.
